## New features and improvements

- Production verification now recognises an owner thinking exception in a sealed qualification receipt. A profile whose thinking row ran in its excepted form (`capability/thinking_excepted`, which records rather than requires a thinking-off reply without reasoning) must carry a valid, unexpired `thinking_exception` record that matches the one in that case's detail; a record without that case, or that case without a record, is refused. Every other capability case stays strict, and speculative-decoding and prefix-cache exceptions are still never accepted. PR #131.

- Added the `v0.1.0` engine source tree (`crates/`, `Cargo.toml`, `Cargo.lock`, `third_party/`, `rust-toolchain.toml`, `.cargo/`, `SOURCE_BUILD.md`, `SOURCE_IDENTITY.json`, `THIRD_PARTY_NOTICES.md`), the tester-agent quickstart in `AGENTS.md`, and structured tester issue templates under `.github/ISSUE_TEMPLATE/` directly to `main`.

- The engine source tree on `main` (`crates/`, `third_party/`, `testdata/`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/`, `SOURCE_BUILD.md`, `SOURCE_IDENTITY.json` and the cluster examples under `docs/examples/`) now matches the v0.1.1 engine commit `75031112ba1279b6da97d5604be5160648cc9f2c` (tree `519678470f283dd5d39281d7d90df8bbc31999e8`, dev engine release `engine-v0.1.1-75031112`), the build every v0.1.1 runtime is sealed on. It also ships `rustfmt.toml` and `tools/switch_registry.json`, so the tree passes its own `cargo fmt --check`, clippy and unit tests. The files are byte-identical to the engine-source archive the v0.1.1 approvals pin. Added by #147.

- The engine source now includes an early version of REXL3's own EXL3 quantizer (`crates/quant`, which builds the `rexl3-quant` command). In v0.1.1 it ships as source only: no prebuilt binary and no user guide yet, and the packs in this release were not produced with it. A guided quantizer is planned for a later release. Added by #147.

- The RED-SNOW-5.3-Flash two-node profile (#127) and the GLM engine pieces it uses (P2 prefill for every expert format of that pack, the pool-page prompt cache, the modelled activation reserve, the embedding table read in place) were built as our own implementation with @justincasey's patch and measurements in #95 as the reference.

- Increased the production `verify` workflow timeout from 10 to 30 minutes so authenticated development asset downloads and runtime verification can finish as the registry grows.

## Bug fixes

- Production verification now accepts a carried gate whose source run was launched from another folder. This only applies when the receipt pins the source run's launch observation and both launches are the same profile choice once absolute folder paths are taken out; any other launch difference is still refused. Bit-identity records also accept the reviewed earlier runtime id. This matches the development sealer (REXL3/REXL3-dev#343, #344), so requalified receipts composed there verify in production. PR #135.

- Production verification now accepts gate receipts carried forward to a new engine build. A carried gate's evidence keeps the release lock and run paths of the build it was measured on, which change with every binary, so no carried gate could verify before. It is still bound to the model pack, profile choice, capabilities, topology and context, and to a registry-pinned source approval. A carried gate may also come from a lock that only gained a role the profile choice does not fetch, and quality and context may carry to another choice of the same bundle when that choice's fresh exactness gate proves drafted equals serial and cached equals cold at the full window. PR #102.
- The engine corresponding source now includes `rustfmt.toml` and `tools/switch_registry.json`, which the source's own format check and two engine tests read. Reported by @Blackwellboy in #84. PR #102.

- Production verification now accepts a carried qualification gate whose source is a complete, all-pass bundle of an earlier engine build that was never sealed, when the evidence also holds a bit-identity record showing the new build answers that bundle binary's requests with identical outputs, a full-window request included. Before, a carried gate needed a registry-pinned sealed approval of the earlier build. Exactness and prefix-cache checks still always re-run. The release tools also gain a one-time pin tool for registry entries sealed before carry-forward existed. PR #116.

- Production verification now carries the GLM-5.3-Flash v0.1.0 qualification gates across two reviewed renames that changed no serving input: the single and two-node entries were split into their own runtime ids, and both were renamed to the `glm53-flash-sage-2.25` and `glm53-flash-tp2-sage-2.25` ids with the pack repository moved to `r0b0tlab/GLM-5.3-Flash-EXL3-SAGE-2.25bpw` (same revision, same files). Every other identity key stays strict, and the pack records must still match exactly. PR #115.

- A model folder whose runtime was renamed can now hold versions sealed under both ids. `MODEL.json` names the runtime's current id; production verification accepts a tree sealed under the earlier id only through its exact reviewed pair in the runtime-id alias table, for a profile choice that tree seals, and refuses any other mismatch. When the first version under the new id is promoted, `tools/promote_runtime.py` moves `MODEL.json` to the new id (and to a reviewed pack-repo rename) only if nothing else changes and every sealed tree in the folder still matches. This lets GLM-5.3-Flash version 2 (`glm53-flash-sage-2.25`) be promoted beside version 1 (`glm53-flash-2.25bpw-sm121`). PR #138.

- `tools/promote_runtime.py` can now promote a later version of a model that is already on `main`. It used to refuse with `existing LATEST differs` whenever `LATEST` named an earlier version, so no requalified version could be promoted. It now moves `LATEST` forward from `v<M>` to the new `v<N>`, and still refuses a `LATEST` that names a later version, is malformed or is not a regular file. PR #137.

- Production sealing and verification now refuse development engine release tags and pre-release native engine versions. Approvals backed by an engine release must name a stable version, while unsealed source-bundle evidence remains supported. PR #118.

- The template allow-list (`runtimes/templates/APPROVED.json`) now accepts a list of approved digests per template version as well as a single digest. Template `v1` lists both the digest the existing trees were sealed against and the digest the v0.1.1 approvals were sealed against, so promotion, carry-source pinning and verification accept the new approvals without re-sealing the existing trees. An unlisted version or digest is still refused. PR #125.

- Engine build: `crates/cuda/build.rs` runs at most Cargo's job count of `nvcc` processes instead of one per stale kernel file, and drops the AArch64-only host flag when the target is another architecture (#83, reported by @Blackwellboy).
- Engine source archive: it now ships `rustfmt.toml` and `tools/switch_registry.json`, and workspace clippy passes, so the archive passes its own `cargo fmt --check`, clippy and unit tests (#84, reported by @Blackwellboy; the exporter half landed in #102).
- `--allow-unvalidated-pack` is required for every family, including unlisted DeepSeek-V4.1 and Qwen3.5-MoE packs (#86, reported by @Blackwellboy).
- DeepSeek-V4.1: Engram table mappings are unmapped at the address and length `mmap` returned (#90); a `prompt_logprobs` readout over 64 tokens and the n-gram splice on a short context no longer panic (#91); the device total counts the shared RoPE tables once (#97); three comments and the boot-margin note match the code (#98). Reported by @Blackwellboy.
- `rexl3-cluster`: `--all` on `up`, `down`, `supervise`, `logs`, `exec` and `env` is refused by name, and a short top-level `memory.min_free_gib` list is refused instead of checking the missing ranks against 0 GiB (#92, reported by @Blackwellboy).
- `/v1/decisions`: an explicit `null` description or yes/no text reads as absent (#93, reported by @Blackwellboy).
- Speculation: the draft cost model prices 9- to 15-row blocks correctly (#96), and the arbiter's copy probe can no longer take a round to `max_rows + 1` (#100). Reported by @Blackwellboy.
- Server: a panic on a tensor-parallel group's engine thread leaks the engine like every other fatal exit, instead of dropping it before `die()` answers (#101, reported by @Blackwellboy).
- Tests: the vision mutation tests pass in a default debug build (#99, reported by @Blackwellboy).

## Known issues

- DeepSeek-V4.1-Flash-1017 two-node: image input is refused under a temporary exception until 2026-12-31 (the quantized pack failed a solid-colour probe); at temperature 0 the model can repeat a phrase until `max_tokens`, so use the sampling defaults for long reasoning and bound replies with `max_tokens`.

- **DeepSeek-V4.1-Flash-1017: the pinned pack revision is gone from Hugging Face.** Both DeepSeek-V4.1 runtimes (`deepseek-v4.1-flash-1017` v1, single node, and `deepseek-v4.1-flash-1017-tp2` v1, two nodes) pin `vcruz305/DSV4.1-Flash-1017-SAGE-REXL3-1.55bpw` at revision `cba79c67582950ea44a4a449b3bb85b800748a35`. The repository's history was rewritten, so the Hub now answers 404 for that revision and `setup --accept-model-download` fails with `MODEL_DOWNLOAD_FAILED`. The repository's only revision, `c40cf25cc3148bae95ac27483505c883840bf8a7`, holds the same files: all 24 files in `model.lock.json` have the same size and SHA-256 there (the 19 large files compared by the Hub's LFS SHA-256, the 5 small files hashed after download). It only adds `README.md`, `LICENSE` and `.gitattributes`, which the runtime accepts beside the pack.
- **Workaround:** download `c40cf25c` yourself and point the runtime at it with the `model_dir` site field. The runtime checks every file against the sealed `model.lock.json` (sizes, SHA-256, index and the engine's fingerprint), not the revision name, so this is the same check a managed download gets. See the pack sheets for the commands. Single node: one copy. Two nodes: a complete copy on each node, named by `nodes.leader.model_dir` and `nodes.follower.model_dir`.
- Reported by @Blackwellboy in #128, who also hashed the 24 files first. Added by #148.

- GLM-5.3-Flash two-node: the HTTP endpoint listens on the leader's address from the site file, not on `127.0.0.1`, and the server has no API key. Run it only on a private, trusted network, or behind a firewall or an SSH tunnel. The pack sheet states this; thanks to @Blackwellboy for the report in #114.

- Ling-3.1-Flash-1019: With `chat_template_kwargs.enable_thinking` false, the model still writes reasoning text and a stray `</think>` into the answer (model behaviour; maintainer-granted thinking exception, expires 2026-12-31). Workaround: keep thinking on, or strip everything up to the last `</think>` from the content. The release qualifier's context, prefix-cache, tool, speculation and smoke checks ran with thinking on under that exception.
- Ling-3.1-Flash-1019: `launch.sh start` re-hashes the ~107 GiB pack just before boot; the page cache this leaves can make the engine plan its KV cache below the 262,144-token window and refuse to start. Workaround: free the file cache before start (for example `sync; echo 1 | sudo tee /proc/sys/vm/drop_caches`). A launcher fix ships in v0.1.2.

- RED-SNOW-5.3-Flash two-node: with thinking off the model may answer a tool request from memory instead of calling the tool (a replay of three such cases with thinking on called the right tool); some replies after a tool call start with reasoning text that ends in a closing think tag.

- Install on a stock Ubuntu 24.04 arm64 image: every shipped recipe pins `libnvidia-compute-580` and `nvidia-utils-580` at exactly `580.173.02-0ubuntu0.24.04.1`, the build the releases were qualified on, and that package version is no longer offered. Ubuntu's archive now serves `580.178.04-0ubuntu0.24.04.1`, and NVIDIA's CUDA repository's `580.173.02-1ubuntu1` is a different version string that the pin does not accept. On such a host `./launch.sh install-deps` and `./launch.sh doctor` refuse (exit 20), and `setup` and `start` refuse with them. Single node, workaround: `./launch.sh print-command --profile <profile>` prints the profile's `rexl3-serve` argv, and running `bundle/bin/rexl3-serve` with that argv starts the server. This skips the controller's dependency, model and readiness checks, and results on another driver build are not covered by the release's qualification evidence. Two nodes (attested TP=2): the rank's native-identity check requires the qualified build, and there is no workaround in this release. A tested driver range (a minimum and a maximum build, each run on a GB10, with `doctor` failing outside it) is planned for a later release. Reported by @Weschera in #109 and confirmed on the Qwen3.8-27B recipe by @ExileAI.
- DeepSeek-V4.1, `--kv-dtype fp16`: prefill is much slower than with the shipped `q4` or with `int8`. Tester measurement (one GB10, the `dsv41-single-262k` argv with only `--kv-dtype` changed, `--slots 1`, a 33,015-token prompt, 3 runs per dtype): 1,516.5 tok/s (`q4`), 1,522.8 (`int8`), 647.1 (`fp16`); decode 27.3, 27.3 and 26.0 tok/s. The cause has not been confirmed. No shipped profile uses `fp16`; keep the default `q4`. Reported by @Weschera in #110.
- DeepSeek-V4.1, `--kv-dtype int8`: still experimental. Not qualified: recall, quality and speed at the full windows (262,144 tokens on one node, 1,048,576 on two) and two-node exactness. A tester measurement found no difference from `q4` at about 65K tokens on one GB10 (needle recall 9/9 at three depths for `q4`, `int8` and `fp16`, identical `long_context` quality, the same prefill and decode speed for `q4` and `int8`), and it is kept as evidence for a future qualification run. Reported by @Weschera in #111.
- DeepSeek-V4.1 with image input enabled (off-profile; both shipped profiles run `--no-vision`): a prompt asking the model to quote text from an image produced a literal `PREFIX` token and non-terminating repeated numbers, deterministically at temperature 0 (3 runs), while other prompts on the same image answered correctly. The same prompt shape transcribed correctly on Qwen3.8-27B, whose vision code is separate. Keep `--no-vision`; this is a blocker for turning DeepSeek-V4.1 vision on. Reported by @Weschera in #112, with the cross-family run by @ExileAI. Added by #148.

- Qwen3.8-Flash-Next and Nemotron-3.5-Super-VL: a request that names no reasoning setting does not think, although each pack's chat template would; some earlier documentation said thinking was on by default. To turn it on, send it in `chat_template_kwargs`, for example `{"chat_template_kwargs": {"enable_thinking": true, "reasoning_effort": "xhigh"}}`, which is what their qualification runs sent, and leave room in `max_tokens` for the thinking (the quality runs used 65,536 tokens). Their pack sheets and the user guide (section 5.3) say the same. Added by #149.
